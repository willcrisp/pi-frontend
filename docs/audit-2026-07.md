# Feature audit & UX pass — July 2026

Method: read the tree, then drove the real app (Vite dev server + `test/mock-opencode.js`)
through boot, session switching, a streamed turn, a steer, every dialog and popover,
the two gating modals (injected onto the event stream), and four viewport widths.
`npm run build` is clean. Claims below were checked in the running app, not inferred.

---

## Verdict

The **architecture is in better shape than the surface**. The store split, the
`HANDLERS` table, and the run-settling design are genuinely extensible — adding an
event, a route, or a preference is a one-file change, and the layering holds (verified:
no upward or sideways imports inside `stores/opencode/`). What needs finessing is the
last mile: five dialogs break their own documented Escape contract, the shell has no
responsive behaviour at all, four failure paths are console-only, and the
permission modal — the thing standing between an agent and your filesystem — is the
least-designed screen in the app.

It feels good to use at ≥1100px on a healthy server. It degrades badly, and
silently, outside those conditions.

---

## 1. `abortSession()` reports success it never checked

`stores/opencode/session.js:60` — the stop button.

```js
await apiPost(`/session/${sessionID}/interrupt`);   // res.ok never read
} finally {
  opencodeStore.isStreaming = false;               // claimed regardless
  markStopped(sessionID);
}
```

`apiPost` resolves for a 4xx/5xx, so a rejected interrupt takes the same path as a
successful one: the square becomes a send arrow and the sidebar dot goes quiet while
the agent keeps working. Within 4s `reconcileRunState()` finds the session still in
`GET /session/active` and flips both back — producing exactly the stop→send→stop flap
that `run.js` was written to eliminate.

This is also the one place that decides a run is over outside `run.js`, which
`CLAUDE.md` names as the sole authority. Route it through the same confirmation: post,
check `res.ok`, set `opencodeStore.error` on failure, and let the poll settle the flag.

`setAgent()` (`session.js:75`) has the same shape — the picker shows the new agent
after a failed switch, with a `console.warn` as the only record.

## 2. A failed transcript load shows you another session's messages

`stores/opencode/messages.js:41` — `connectToSession()` clears drafts, children,
revert state, steers and context, but never `opencodeStore.messages`. `refreshActiveMessages()`
returns early on failure (`messages.js:89`, console-only), so the previous transcript stays.

Reproduced: with `GET /session/ses_mock2/message` failing, clicking **Second session**
leaves all five of *Mock session*'s messages on screen under the new title, no error,
no empty state. `shots3/10-stale-transcript.png`.

`fetchSessionMessages`' own comment warns callers not to treat failure as "no
messages" — the other half of that (don't keep the wrong session's) is unhandled.
Needs a per-session loading/error state on the transcript; there is currently no
loading state at all, so even the success path flashes stale content on a slow
SSH-forwarded server.

## 3. Escape closes five dialogs and not the other five

`ShortcutsDialog` promises **`Esc` — Close the open menu or dialog**
(`shots2/10-shortcuts.png`). Measured, in the app:

| Closes on Escape | Does not |
|---|---|
| CommandPalette, ShortcutsDialog, QuestionDialog, ConfirmDialog, HandoverDialog, ImageAnnotator, FilePreview, SelectMenu, SshPopover, ColorProfilePopover, both composer menus | **ProvidersDialog, SubagentsDialog, SavedPermissionsDialog, UsageDialog** |

The four hold-outs share the `.connect-backdrop` markup and a `@mousedown` handler but
never registered a key listener. Since they already share a wrapper class, the fix is
one shared `useDialogEscape()` composable rather than four copies.

Secondary: `ConfirmDialog` and `HandoverDialog` put `@keydown.escape` on the backdrop
`<div>`, which is not focusable — they work only because something inside autofocuses.
Click the backdrop once and Escape is dead. Same composable fixes it.

## 4. The permission modal is the least-finished surface in the app

Side by side, same class of interruption, both injected with realistic payloads:

- `shots3/02-question-dialog.png` — header chip, `1 / 2` progress, numbered options,
  per-option descriptions, number keys, Enter, Escape-to-skip. 362 lines.
- `shots3/01-permission-dialog.png` — `Action: bash`, a resource list, `JSON.stringify(metadata, null, 2)`,
  three same-weight buttons. 88 lines.

Concretely, on `PermissionDialog.vue`:

- **No keyboard at all.** No autofocus, no Enter, no number keys. The most frequent
  interruption in the app is the only mouse-only one, in an app otherwise built for
  the keyboard.
- **Queue depth is invisible.** Two requests were pending in the screenshot; nothing
  says so. `QuestionDialog` shows `1 / 2` for the same situation.
- **No session attribution.** `sessionID` is captured (`permission.js:26`) and never
  rendered. A sub-agent, or a chat in another project, can ask you to approve
  `rm -rf` and the modal looks identical to one from the chat you're reading.
- **"Allow always" is styled exactly like "Allow once"** while `Deny` is the quiet
  secondary. The permanent grant is the easy mis-click, and the way back is a
  padlock icon in the sidebar you have to know about.
- The resource list and the metadata dump repeat the same command, and a destructive
  command gets no different treatment from a `webfetch`.

This is also the highest-risk untested surface: `test/` has nine specs and none
covers permission or question, and `mock-opencode.js` emits neither event. A
regression here doesn't degrade the UI, it hangs the agent.

## 5. No responsive behaviour in the shell

Four `@media` rules exist in the whole app (`UsageDialog`, `ProvidersDialog`,
`find-bar.css`, and a `prefers-reduced-motion` in `d20.css`). The sidebar, header and
composer have none. Measured at 420×860:

```
sidebar    260px   (fixed, never collapses)
chatPanel  160px
headerRight  106px wide, at x=356 — outside the 160px panel
document.scrollWidth 569  vs  clientWidth 420   → the page scrolls sideways
```

Visible consequences (`shots2/19-width-420.png`): header controls clipped mid-icon,
composer placeholder cut off mid-line, and every user prompt breaking after its first
character. That last one has its own cause — see below.

## 6. An invisible, clickable, focusable button on every user message

`MessageView.vue:280`:

```css
.msg-revert { float: right; opacity: 0; }
.msg:hover .msg-revert { opacity: 1; }
```

Measured in the running app:

```
opacity 0 · pointer-events auto · tabIndex 0 · width 95px
document.elementFromPoint(centre) → .msg-revert
```

So a 95px hit target that stages a revert — the app's one destructive action — is
present and hit-testable on every user turn while invisible, and sits in the tab order.
It also occupies layout: at 420px it consumes the whole first line, which is why
"show me a snippet" renders as `s` / `how me a` / `snippet`.

`visibility: hidden` (or `display: none` toggled on hover/focus-within) fixes the
hazard, the tab order and the wrap in one change. Keep it reachable by keyboard via
`:focus-visible` so it doesn't become mouse-only.

## 7. Two different token counts for the same session, on screen at once

`shots2/07-usage-dialog.png`: the usage popover says **Session tokens 0 / $0.0000**
while the dialog behind it lists the same *Mock session* at **$0.4200 / 35.0k**.

Both are correct and neither is labelled: the popover reads `store.sessionStats`
(event-derived, zero until a turn runs in this page load), the dialog reads
`SessionV2.Info.cost/tokens` (server cumulative). `CLAUDE.md` warns the two must not
be confused — the UI puts them 200px apart with near-identical wording. Label them
("this page load" vs "all time"), or have the popover fall back to the server figure
when no turn has streamed yet.

Also: the popover stays open behind the dialog it launched.

## 8. The session list never refreshes itself

`fetchSessions()` is called on boot, on the ⟳ button, on create, and on sub-agent
drill-in — never from an event (`session.created` is handled in `children.js:70` only
for parent linkage; there is no `session.updated` handler).

So on the single most common flow — new chat, first prompt — the server auto-titles the
session and the sidebar keeps showing `New session - 2026-07-30T…` until you press ⟳
or reload. `ChatHeader.vue:32` hides that placeholder and shows nothing; the sidebar
shows it raw. Same staleness makes every figure in the Usage dialog one refresh behind.

## 9. Failures that only reach the console

Everything below leaves the UI looking like a normal empty result. `App.vue` already
has an error banner bound to `opencodeStore.error`; these paths just don't use it.

| Path | Symptom |
|---|---|
| `projects.js:64` session list | empty sidebar, reads as "no sessions" |
| `messages.js:90` transcript | see finding 2 |
| `session.js:67` interrupt | see finding 1 |
| `catalog.js:59/81/91/102` catalogs | empty model/agent pickers, or none at all |

The catalog case is worth distinguishing from the empty-state it collides with:
`App.vue:71` shows "No models available yet — connect a provider" when
`availableModels` is empty, which is also what a failed `GET /model` produces. A user
whose server hiccuped is told to go add a provider they already have.

## 10. Smaller things

- **`.header-title-content` is `display: flex`**, so the `" · "` separator spans have
  their edge whitespace trimmed as flex items. Renders as
  `Mock session·120 in / 12 out· 0% ctx` — glued on one side, spaced on the other
  (`shots2/18-width-600.png`). Join the parts in a computed string, or use `gap`.
- **One feature, three names**: sidebar tooltip "Providers", dialog heading
  "Integrations", empty-state button "Add a provider".
- **A customer's gateway is the shipped default**: `https://gateway.ai.fortescue.com`
  is prefilled in both ProvidersDialog and UsageDialog. Fine for one deployment,
  wrong for a general harness — belongs in config, not a `value=`.
- **Internal errors reach the user verbatim**: the Sub-agents dialog opens with
  `pty create response had no id` in red whenever PTY isn't reachable
  (`shots2/02-dialog-sub-agents.png`). No explanation, no retry.
- **No keyboard interrupt.** Verified against a slowed mock run: Escape leaves the
  stop square in place whether the composer or the transcript has focus. Stopping an
  agent is mouse-only, in an app that ships a shortcuts dialog.
- **The composer placeholder is a random literary quote**, so the one piece of
  always-visible copy in the app never says what the box does — and at narrow widths
  it clips mid-sentence. Worth keeping the flavour on a returning-user empty state
  and giving first-run something instructive.
- **Docs drift**: `fork.js`, `shortcuts.js`, and `stores/opencode/drafts.js` exist but
  aren't in the `CLAUDE.md` module tables.

## Is it simple, yet extensible?

**Yes, and this is the strongest part of the codebase.** Verified rather than assumed:

- `stores/opencode/` imports run strictly downward — a script over every relative
  import found zero upward or sideways edges against the documented order.
- No component or composable reaches past `stores/opencode.js`; the facade holds at
  every call site.
- `events.js` really is a table. 40-odd entries including explicit no-ops that say
  "seen, nothing to do", with two build vocabularies normalized on the way in
  (`canonicalType`) so one table serves both. Supporting a third build is one entry.
- The `run.js` header is the best comment in the repo: it records the captured event
  sequence, the two builds that disagree, and why a terminal event is a candidate
  rather than an answer. That's the sort of note that stops the next person from
  reintroducing the bug.
- 24 style partials for 24 `@import`s, one per feature.

Two real fragilities against that:

1. **`opacity: 0` and `float` used as layout-safe hiding** (finding 6) is a pattern,
   not a one-off — worth a sweep.
2. **The load-bearing CSS import order** is honestly documented but still means a
   flat namespace of equal-specificity selectors where correctness depends on file
   order. It works at 24 partials; it is the thing most likely to bite at 40. Nothing
   to do today beyond preferring `<style scoped>` for new components, which
   `CLAUDE.md` already says.

## Does it feel good to use?

Walking it end to end at 1440px: **yes, and distinctly so.** The things that land:

- **It boots straight into work.** A reachable server means no connect screen at all —
  `App.vue` probes, connects, and restores your last session. The connect gate only
  appears when it's actually needed.
- **The transcript is calm.** Collapsed thinking as one italic line with a word count
  (`thought · 15 words`) is the right default — enough to see the turn is on track,
  not enough to bury the answer.
- **Steering is a real feature, not a queue.** Typing into the same box mid-run, with
  the pill counting admitted-but-not-yet-promoted prompts, is better than most agent
  UIs manage.
- **The prompt rail** in the left gutter is a quietly excellent piece of navigation.
- **QuestionDialog** is the best screen in the app and should be the template for the
  other modals.
- The d20 is a good joke and costs nothing.

What undercuts it, in the order a user would hit it:

1. A first-run user is told to add a provider by a dialog called Integrations, prefilled
   with someone else's gateway (findings 9, 10).
2. Their first chat has no name in the sidebar for as long as they don't press ⟳ (8).
3. The first agent action needing approval opens the app's least-designed modal, which
   they can't answer from the keyboard, and which won't tell them which session is
   asking (4).
4. Stopping the agent needs the mouse; Escape does nothing (10).
5. If anything goes wrong on the wire, the app looks empty rather than broken (2, 9).
6. On a laptop at half-screen or a tablet, the layout falls apart (5, 6).

## Suggested order

**Correctness, small diffs:** 1 (`abortSession`), 6 (`visibility: hidden`),
10 (header spacing), 3 (shared Escape composable).

**Then the honesty gap:** 2 (transcript loading/error state), 9 (route failures to the
banner), 7 (label the two token figures).

**Then the design work:** 4 (bring `PermissionDialog` up to `QuestionDialog`'s level,
with specs and mock events to match), 5 (a collapsible sidebar and a wrapping header),
8 (refresh the session list on `session.updated`).
